## Evidence in the checkout

`probar_webb.py` defines `leer_exposicion(ruta, uri)`. It merges primary and SCI headers, checks NRC_IMAGE, position, pointing and SCI validity, and returns a full-resolution Pillow image and metadata dictionary. The driver shuffles public science observations in its fixed 2025-01-01 to 2026-02-01 search interval, samples up to 20, deduplicates product URIs within the run and saves FITS downloads and PNG/JSON pairs in `salida_webb_exp_2`. This harvesting stage records measurements; the separate owner review function `es_apta(metricas)` decides visual eligibility. Its exact rule is now versioned as [`visual-filter-1`](../scripts/visual_eligibility.py): accept when background brightness is at most 45/255, or when brightness is below 90/255 and normalized total jump is at most 0.10. Its Earth-relative estimate subtracts an Astropy Earth barycentric vector at the elapsed midpoint from header Webb XYZ, whose epoch is recorded separately.

`recalcular_metricas_webb.py` imports that reader, opens existing JSON and sibling FITS in `salida_webb`, rebuilds the PNG in memory and atomically replaces only the metrics in the JSON. Other fields, including any pre-existing eligibility decision, can therefore describe an earlier pass. The separate filtering script was not present in this checkout; the owner supplied its exact `es_apta` function, which is retained as the canonical versioned implementation in `scripts/visual_eligibility.py`.

The increment-4 collector applies the owner's separate `es_apta(metricas)` rule after `leer_exposicion`: brightness ≤45 passes directly; brightness from 45 to below 90 passes only when `salto_total` ≤0.10; brightness ≥90 or a missing/non-finite required value fails. `stripesWarning` at `salto_total >= 0.19` remains a descriptive metric and is not itself a rejection when the low-brightness branch passes. F140M-only selection, a 150 MiB ceiling and NRCA3 preference are not part of this visual rule and are not applied. Increment 4 also requires a usable calibrated image, evaluable ASDF/GWCS metadata to map the detector footprint onto the sky, and spacecraft ephemerides to place the orbital illustration; these are technical rendering requirements.

## Time, image and sky construction

Prefer valid MJD-MID, then EXPMID in the product's documented time system, converting to UTC. Check finiteness, begin ≤ middle ≤ end and header semantics. Otherwise compute begin + half the elapsed interval with a time library and record the method. Preserve original header values and time keys for audit. EPH_TIME has its own epoch and scale, to be verified from the applicable product definition. [JWST time definitions](https://jwst-docs.stsci.edu/accessing-jwst-data/jwst-science-data-overview/jwst-etc-time-definitions)

Evaluate model.meta.wcs on the calibrated detector grid, x = column, y = SCI row, zero-based pixel centers. For width W and height H use ((W−1)/2,(H−1)/2) and the ordered boundary vertices (−0.5,−0.5), (W−0.5,−0.5), (W−0.5,H−0.5), (−0.5,H−0.5) subject to the calibrated bounding box. Validate finite support there and record actual bounds if a valid subregion is used. No implicit FITS display flip. Full-frame reduction preserves angular footprint. For any future crop/flip, store the explicit displayed-to-detector transform and recompute displayed center and corners. [JWST calibrated WCS](https://jwst-pipeline.readthedocs.io/en/stable/jwst/assign_wcs/main.html)

Classify the center by the official constellation region and record the boundary implementation/version. The conventional stick figure is a separate dataset. Shared sky resources carry immutable key, release/digest, source file and upstream attribution/license, frame/equinox, epoch, magnitude band and any coordinate conversion. Store stars as ICRS RA/Dec degrees and magnitude, and stick edges as ordered sky endpoints or stable star ID pairs. Normalize RA to [0,360), Dec to [−90,90]. Convert source longitudes explicitly.

**Chosen sources for increment 4 (audited 2026-11-26):** use [HYG v4.1](https://github.com/astronexus/HYG-Database/tree/main/hyg/CURRENT) for reference stars, filtered to visual magnitude ≤6.0, and use the `constellations.lines.json` dataset from [d3-celestial](https://github.com/ofrohn/d3-celestial) for constellation figures. HYG's owner licenses v4.1 under CC BY-SA 4.0; include attribution and license, and apply CC BY-SA 4.0 to the filtered/adapted star data. HYG records RA/Dec for epoch 2000.0 and apparent visual magnitude; convert RA hours to ICRS degrees, keep Dec in degrees, exclude the Sun (`dist=0`), and preserve a stable source row ID. The d3-celestial lines are distributed with a BSD 3-Clause notice and attributed in that project's data README to the IAU constellation material with the author's modifications. Pin both datasets to commits and retain their source notices. [HYG licence and format](https://github.com/astronexus/HYG-Database/blob/main/README.md) · [HYG v4.1 data](https://github.com/astronexus/HYG-Database/blob/main/hyg/CURRENT/hygdata_v41.csv) · [d3-celestial data sources](https://github.com/ofrohn/d3-celestial/blob/master/readme.md) · [d3-celestial licence](https://github.com/ofrohn/d3-celestial/blob/master/LICENSE)

## Renderer interface review for increment 4

The headless shared entry point already exists as `renderCard(scene, details, photoDataUrl, sky, skyDisplay?)` in `src/card.ts`; the Worker calls the same function from `worker/src/index.ts`. It performs no fetches and returns the complete card SVG. `renderSkyPanel` accepts geometry and catalog arrays through `SkyPanelScene` plus optional display labels, and the orbital renderer returns SVG from a `Scene`. This is a proven synthetic-fixture seam, not yet the real-data contract.

The production caller should keep the one `renderCard` entry point but pass a single resolved-card input assembled by the host before rendering. That input must carry: observation/display metadata and credits; photo bytes, MIME, source/output dimensions and detector-to-image mapping; the calibrated sky center/footprint, region, versioned line/star subsets and detail window; and the common-epoch orbital vectors, camera basis, pointing direction and resolved tracks. The host validates the manifest and resolves resource keys. The renderer receives no bucket keys, network clients or unresolved external resources. It embeds the validated raster and returns one complete SVG.

**Gaps found in the current implementation:**

- `CardDetails` is fixture-oriented (`variant`, `seed`) and has no provenance/credit, constellation, exposure time basis or version data. `photoDataUrl` is an unchecked string rather than validated photo bytes plus MIME/dimensions/mapping.
- `SkyFixture` is explicitly synthetic and contains fixture-only labels/tags. `SkyPanelScene` now exposes the required geometry independently, and `skyDisplay` can provide the field-region heading and coordinate caption. The real resolved sky data still needs source release/digest, magnitude band, attribution, region and validated WCS-derived footprint. The full card description and other fixture-only labels still need to become data-driven.
- `Scene` includes vectors and tracks, but `renderOrbit` currently derives displayed bodies and paths from synthetic `phases`; it does not render `earth`, `moon`, `webb`, `l2`, or the track arrays. It treats the first two components of `pointing` as screen coordinates rather than projecting the documented ecliptic vector through the camera basis. The real orbit renderer must map physical anchors and tracks using the fixed camera and one declared local magnification.
- The standalone card slices the orbit SVG and nests its children, while several orbit text styles are supplied by `src/style.css` selectors. A self-contained card must carry those styles inside the SVG or inline them; it cannot depend on the playground page stylesheet.
- TypeScript interfaces do not validate runtime bundle values. Before calling the renderer, the real host must reject malformed keys, wrong tuple lengths, non-finite coordinates, invalid photo MIME/bytes and inconsistent dimensions, and must withhold scenes with missing required data.

Keep the existing synthetic `renderCard` call working for playground and Worker fixtures while introducing the resolved production input through an explicit adapter or overload. Do not make the renderer load FITS files, interpret archive headers, query Horizons, resolve buckets, or choose catalog revisions. This keeps renderer output deterministic from fully resolved inputs and lets the production card use the same composition as both existing synthetic clients.

Construct the north-up, east-left gnomonic detail window at field center. Use local east/north axes and fix the roll convention at a pole using the recorded central RA. Fit the footprint's projected width and height to about one third of the detail rectangle on its limiting axis, preserving panel aspect. Record center, angular spans through center and inverse-projected screen corners in top-left clockwise order. Clip great-circle line segments against the window even when both endpoints are outside. Draw only catalog stars. A sparse detail may legitimately show just the field and scale bar.

First fit a hypothetical single overview around the union of the stick figure and field. Use a spherical projection centered on that union (e.g. stereographic), with local north up and east left. Project edges on the sphere across RA zero, resampling as needed. Measure the shorter side of the minimum-area oriented bounding rectangle of the projected field. At a proposed reference width of **540 CSS px** (half the SVG base), use single-map true scale if that side is ≥12 display pixels. This configurable visual cutoff belongs to the render version. A static GitHub SVG makes one decision per exposure and layout.

Otherwise fit the overview to the figure, footprint and detail-window outline on the left, link left to right and draw the aligned detail on the right. Use the actual inverse-projected window polygon for the outline and the detector polygon for the purple fill. When subpixel, add a distinct locator labeled as symbolic. Compute the scale bar from inverse projection at its drawn location. Include outside-figure targets in the fit. Test wrap and polar geometry in spherical coordinates.

For a real card whose target detector footprint is much smaller than the constellation, keep the established two-panel composition: show only the target constellation stick figure and white stellar vertices in the overview, then a moderate five-degree local reference view centered between the pointing and nearest figure vertex. The single purple outline in the overview selects this detail window. In the local view, put a separate adjustable symbolic square at the real pointing center and label it “not to scale”; preserve the exact detector WCS footprint in resolved inputs. Tune the overview multiplier and local symbolic-square size in `src/real-card-presentation.ts`. Do not enlarge the sky view to detector scale or add contextual catalog stars without a design decision. For the lower panel, call the increment 1 compact renderer unchanged and adapt the resolved exposure-time Earth, Moon, Webb and field-pointing vectors to its phase and direction controls. This deliberately moves the existing markers without redrawing its schematic curves or changing its composition. Preserve the full Horizons vectors and time-tagged tracks in the offline bundle for later track rendering.

## Orbital scene

At the chosen local exposure midpoint convert `MJD-AVG` from UTC to TDB. Do not use the JWST `TDB-MID` value as the spacecraft query epoch: that header value includes the barycentric correction (`BARTDELT`). Request geometric Horizons vectors (no light-time or aberration correction), Sun center, J2000 ecliptic axes, km and km/s, Earth center, Moon center and spacecraft at the identical epoch. Check returned target, center, axes, timescale, units, coverage and epochs. Store a zero Sun and approximate L2 = earth + 1,500,000 km × normalize(earth). Label this radial estimate. Preserve the independent barycentric header record. Rotate the field's ICRS unit vector into J2000 ecliptic axes with a documented rotation only, without observer translation or parallax. Missing spacecraft coverage leaves a technical omission. [JWST orbit](https://jwst-docs.stsci.edu/jwst-observatory-characteristics/jwst-orbit) · [Horizons API](https://ssd-api.jpl.nasa.gov/doc/horizons.html)

For real calibrated JWST images, use `meta.wcs` from the FITS ASDF extension through GWCS. The header FITS WCS is only a simpler representation and does not encode all transformations in the image pipeline. Preserve both the pixel center and the top-left clockwise detector corners from the GWCS result. The reproducible tool pins and a real FITS/Horizons check are recorded in the increment 4 evidence.

The first real preload is retained under [`docs/evidence/increment-4/real-bundle/`](evidence/increment-4/real-bundle/). Its offline renderer consumes the resolved observation, sky, orbit and reduced-raster files only. The Horizons response snapshot preserves each requested JD TDB and geometric vector; rebuild the same bundle with the `--offline` flag after acquiring the local FITS, PNG regression reference and audited source files. Orbit tracks record time-tagged samples; the compact card uses only the exposure-epoch state vectors to set the existing marker positions and pointing. The track samples remain available in the bundle, but are not drawn in the card.

Each shared series has key/revision, source/query, center, frame, basis, km units, time scale, validity interval, cadence and sorted samples [JD TDB,x,y,z]. Batch neighboring epochs and reuse immutable intervals. Earth uses a heliocentric year with anchors at actual calendar dates. Moon uses Moon minus Earth over roughly a lunar revolution in fixed ecliptic axes. For Webb use about six months of Webb minus radial L2. At **each sample epoch**, compute R = unit(earth), N = unit(earth × earthVelocity), T = N × R. Store [offset·R,offset·T,offset·N]. Reconstruct each offset in the exposure-time basis as aR + bT + cN at the exposure's L2. Merge exact exposure-epoch samples into each resolved series from the preload state, preserving chronological order. Draw the historical polyline open. Limit interpolation to validated intervals and accuracy, with no extrapolation across coverage gaps.

Use a fixed orthographic oblique camera looking at the Sun. For a reproducible initial orientation, take horizontal axis U along the ecliptic-plane projection of Earth's July 1 2025 vector, P = ecliptic north × U, vertical-up V = sin(25°)P + cos(25°)north. Map q to (q·U, −q·V) in screen coordinates. Freeze U with its measured source or a labeled synthetic reference in the fixture. Check March below, July right and November above without rotating the camera per exposure. Fit the white Earth track with margin and a yellow Sun. Place green Earth at its physical anchor. Apply one labeled local magnification M to *all* Earth-relative offsets, e.g. draw Webb at earth + M(webb−earth). Use the same M on the cyan Moon track and gray Moon, pale orange antisolar link, L2 dot and Webb track. Anchor the Webb icon and purple pointing wedge there. State the local factor in the legend.

Project the unit pointing vector onto U,V. A triangle indicates direction with illustrative opening angle. When projected length falls below a documented render tolerance, use dot/cross toward/away according to its signed component on U × V. Move labels or offset icons with leaders on conjunctions and near edges, reserve margins or provide local detail. Keep true marker anchors on their tracks. Real Moon and Webb phases come from vectors.

The host resolves photo and shared keys into a scene before rendering. The pure renderer returns one script-free self-contained SVG with embedded PNG, vector shapes, title/description and text, with no external fonts or fetches. In HTML provide descriptive alt (date, field, detector/filter where known), accessible Next and status feedback. Validate size, MIME, keyboard interaction, proxy display and mobile legibility using the [increment checks](increments.md).
